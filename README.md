# N-Queens Visualizer

A **C++17 terminal-based N-Queens Visualizer** that demonstrates how different backtracking techniques solve the N-Queens problem.

The project provides three different solving algorithms, animated terminal playback, step-by-step execution, performance statistics, and algorithm comparison.

- C++17 implementation
- CMake build system
- Terminal-based chessboard visualization
- Standard Backtracking
- Optimized Backtracking
- Bitmask Solver
- Common `ISolver` interface

- Step-by-step playback
- Solver statistics

- Event-generation statistics

## N-Queens Problem

The goal is to place `N` queens on an `N × N` chessboard so that no two queens share a row, column, or diagonal.

Example for `N = 4`:

```text
. Q . .
. . . Q
Q . . .
. . Q .
```

Known solution counts:

| N | Solutions |
|---:|---:|
| 1 | 1 |
| 2 | 0 |
| 3 | 0 |
| 4 | 2 |
| 5 | 10 |
| 6 | 4 |
| 7 | 40 |
| 8 | 92 |
| 9 | 352 |
| 10 | 724 |

## Algorithms

### 1. Standard Backtracking

Places one queen per row and checks each candidate against previously placed queens.

The safety check scans existing queens, making the check approximately `O(N)` per candidate.

**Advantages**
- Simple
- Easy to understand
- Useful as a reference implementation

**Limitation**
- Repeatedly scans existing queens

### 2. Optimized Backtracking

Uses three occupancy arrays:

```text
columns
diagonals
antiDiagonals
```

For `(row, column)`:

```text
diagonal     = row - column + N - 1
antiDiagonal = row + column
```

Safety can then be checked in approximately `O(1)` time.

**Advantages**
- Faster safety checks
- Simple optimization
- Clearly demonstrates the benefit of auxiliary data structures

### 3. Bitmask Solver

Uses `std::uint64_t` to represent occupied columns and diagonals.

Available positions are obtained with bitwise operations:

```cpp
available =
    allColumns &
    ~(columns | diagonals | antiDiagonals);
```

The lowest available position can be extracted with:

```cpp
bit = positions & (~positions + 1);
```

**Advantages**
- Compact representation
- Fast bitwise operations
- Efficient candidate extraction

**Limitation**
- The current representation supports board sizes up to 63.

## Algorithm Comparison
| Feature | Standard | Optimized | Bitmask |
|---|---|---|---|
| Backtracking | Yes | Yes | Yes |
| Column tracking | Direct scan | Array | Bitmask |
| Diagonal tracking | Direct scan | Array | Bitmask |
| Safety check | O(N) | O(1) | O(1)-style |
| Candidate representation | Coordinates | Coordinates | Bits |

All three algorithms should produce the same number of solutions for the same `N`.
  
## Solver Interface

All solvers implement the common `ISolver` interface:

```cpp
generateEvents();
hasMoreEvents();
getCurrentEvent();
advanceEvent();
resetPlayback();
getEvents();
getStatistics();
getSolutions();
```

The application stores the selected solver using:

```cpp
std::unique_ptr<ISolver>
```

This enables runtime algorithm selection and makes the project extensible.

## Event System

The solving process is represented using events:

```cpp
enum class SolverEventType
{
    TryPosition,
    PlaceQueen,
    Conflict,
    RemoveQueen,
    SolutionFound,
    Finished
};
```

Each event can contain:

- Event type
- Row
- Column
- Solution number

This separates solver logic from visualization.

## Complexity

N-Queens is a computationally expensive combinatorial search problem.

### Standard Backtracking

Safety checking scans existing queens:

```text
O(N)
```

per candidate.

### Optimized Backtracking

Occupancy arrays provide approximately:

```text
O(1)
```

safety checking.

### Bitmask

Bitwise candidate calculation is approximately:

```text
O(1)
```

at the machine-operation level.

The overall search remains exponential. These optimizations reduce the work performed at each search node rather than changing the fundamental complexity of the problem.

## Memory Considerations

The application stores solver events for later playback. Therefore memory usage can become significant as `N` increases.

Recommended practice:

- Use smaller boards for visualization.
- Use benchmark mode for larger boards.
- Keep in mind that the bitmask solver supports up to 63 positions, but event storage makes very large boards impractical for this visualizer.

## Design Principles

### Separation of Concerns

```text
Board
  ↓
Solver
  ↓
Events
  ↓
Renderer
  ↓
Application
```

The board manages board state, solvers perform computation, events represent the computation, and the renderer handles terminal output.

### Interface-Based Design

```text
ISolver
   │
   ├── Solver
   ├── OptimizedSolver
   └── BitmaskSolver
```

A future solver can be added without fundamentally changing the application.

### Runtime Algorithm Selection

The application uses:

```cpp
std::unique_ptr<ISolver>
```

so the selected algorithm can be changed at runtime.

## Limitations

### Terminal-Based

The project intentionally uses terminal visualization instead of a GUI framework.

### Event Storage

The complete event sequence is stored in memory for playback.

### Large Boards

Large values of `N` can generate very large search spaces and event streams.

### Bitmask Limit

The current bitmask implementation uses:

```cpp
std::uint64_t
```

and therefore supports at most 63 board positions.
